# Enterprise Documentation Assistant — Project Handoff

This document is a handoff for continuing the project with another AI/coding agent.
It records what has actually been decided and implemented so far, the current architecture, and the remaining roadmap.

The original project brief defines the goal as an enterprise-style documentation assistant built incrementally, with the core RAG system established before LangGraph/FastAPI and with LangSmith integrated early rather than added at the end.

---

## 1. Project Goal

Build a credible portfolio-grade Enterprise Documentation Assistant that lets users ingest documentation/PDFs and ask questions over the uploaded knowledge base.

The intended system will demonstrate:

- Document ingestion
- Document parsing/loading
- Text chunking
- Embeddings
- Vector search
- Metadata-aware retrieval
- RAG-based question answering
- Source/citation information
- Conversation memory
- LangChain
- LangGraph
- LangSmith observability/tracing
- FastAPI
- Docker
- Clean configuration/environment management
- Error handling
- Tests and evaluation
- A production-oriented but not overengineered architecture

The project should prioritize:

**learning → solid engineering → interview defensibility → portfolio quality**

Do not optimize for the number of technologies used.

# 4. Configuration

## 4.1 Decision

Use **Pydantic Settings** for configuration instead of scattering `os.getenv()` calls throughout the application.

The intended flow is:

```text
.env
  ↓
Pydantic Settings
  ↓
Settings object
  ↓
Application components
```

Dependency:

```text
pydantic-settings
```

Configuration belongs in:

```text
app/config.py
```

The configuration layer should remain separate from application/business logic.

## 4.2 Current/Initial Environment Variables

```env
# LLM
LLM_PROVIDER=google
LLM_MODEL=gemini-2.5-flash
LLM_API_KEY=

# Embeddings
EMBEDDING_MODEL=gemini-embedding-001

# LangSmith
LANGSMITH_TRACING=true
LANGSMITH_API_KEY=

```

Important:

- `.env` contains real local secrets and must not be committed.
- `.env.example` contains placeholders/non-secret defaults and is committed.
- API keys must not be placed in source code.
- API keys must not be printed or included in custom trace metadata.

`LLM_PROVIDER` is treated as an internal identifier such as `google`, not as the marketing/product name `Google Gemini`.

# 6. LangSmith

## 6.1 Decision

LangSmith was integrated early, as required by the original project plan.

Do not remove or postpone observability until the end of the project.

Current purpose:

- Observe LLM calls
- Observe RAG execution
- Debug prompts and model behavior
- Attach useful metadata/tags
- Later trace LangGraph execution
- Later support evaluation

The project distinguishes:

### Application logging

Intended for operational concerns such as:

- Errors
- Ingestion status
- Document IDs
- Request IDs
- Timing
- Failures

### LangSmith

Intended for AI-specific observability such as:

- LLM calls
- Chains
- Retrieval/RAG runs
- Prompts
- Token/latency information where available
- LangGraph execution later
- Evaluation/debugging

Custom trace metadata currently uses high-level values such as:

```text
component
environment
```

Do not put sensitive document contents, secrets, or API keys into custom metadata.

## 7.2 Metadata

Metadata currently established on documents/chunks:

```text
document_id
file_name
source
page_number
chunk_id
```

A single `document_id` identifies the source document.

Each chunk receives a `chunk_id` derived from that document ID and chunk position.

This metadata is important for later retrieval filtering and source attribution.

## 7.3 Current Ingestion Modules

Conceptual structure:

```text
app/ingestion/
├── __init__.py
├── loader.py
├── splitter.py
└── service.py
```

Responsibilities:

- `loader.py`: load/validate PDF and add document metadata
- `splitter.py`: split documents into chunks
- `service.py`: orchestrate loading and splitting; later this can grow to include embedding/storage stages

The ingestion package should not own LLM logic, LangGraph logic, or FastAPI concerns.

# 10. Vector Store

## Decision

Use **Chroma** for the current project implementation.

Reasoning:

- Simple local development
- Persistent local storage
- Metadata support
- Straightforward LangChain integration
- Enough capability for the current portfolio/learning stage
- Avoids introducing managed infrastructure prematurely

Alternatives considered:

### FAISS

Good for understanding vector similarity and local experimentation, but less database-like for this project's current needs.

### Pinecone

Reasonable managed/cloud option and already familiar, but not necessary for the current stage.

Chroma was selected for the implementation because it gives a practical vector-store experience without adding cloud operational overhead.

Generated local Chroma data:

```text
.chroma/
```

This directory is ignored by Git.

Vector-store abstraction lives conceptually under:

```text
app/vector_store/
├── chroma.py
└── service.py
```

The rest of the application should call the vector-store service rather than directly depending everywhere on Chroma.

# 12. RAG Pipeline

The current RAG architecture is a basic **2-step RAG** pipeline.

```text
User Question
      ↓
Retrieval
      ↓
Relevant Chunks
      ↓
Context Construction
      ↓
Gemini
      ↓
Grounded Answer
      ↓
Source Information
```

The current RAG system is intentionally not adaptive/agentic yet.

It does not currently implement:

- Query rewriting
- Reranking
- Hybrid retrieval
- Multi-hop retrieval
- Corrective RAG
- Self-RAG
- Adaptive RAG

Those are backlog/improvement options, not current requirements.

Use **Pydantic for application data models**, not `dataclass`.

Replace any remaining application-level dataclasses with Pydantic models where appropriate.

Current conceptual models:

```text

├── file_name: str

├── answer: str
├── sources: list[Source]

`context` is kept available for evaluation/inspection.

# 15. Evaluation Framework

## 15.1 Dataset

An `evals/` directory was created.

Current structure is expected to include:

```text
evals/
├── dataset.json
├── models.py
├── judge.py
└── runner.py
```

The dataset uses three categories:

1. `Answerable`
2. `Answerable but requires combining information`
3. `Unanswerable`

Example dataset case:

```json
{
  "id": "agent-pillars-001",
  "question": "What are the three pillars of modern software agents?",
  "expected_answer": "The three pillars are autonomy, asynchronicity, and agency.",
  "expected_sources": [
    {
      "file_name": "agentic-ai-foundations.pdf",
      "page_number": 10
    }
  ],
  "answerable": true,
  "category": "Answerable"
}
```

For unanswerable cases, `expected_answer` is allowed to be `null`.

## 15.2 Pydantic Evaluation Models

The evaluation dataset is validated with Pydantic.

Conceptual models:

```text
ExpectedSource
EvaluationCase
JudgeResult
EvaluationResult
```

`EvaluationCase` contains:

```text
id
question
expected_answer: str | None
expected_sources
answerable
category
```

`category` is restricted to the three categories above.

## 15.3 Deterministic Evaluation

Current deterministic metrics:

### Source match score

Compares expected `(file_name, page_number)` values with retrieved sources.

### Abstention check

For unanswerable cases, checks whether the system returns the insufficient-information response.

Current abstention message:

```text
I don't have enough information in the provided documentation to answer this question.
```

For answerable cases, abstention is considered not applicable.

## 15.4 LLM-as-a-judge

Two judges were added:

### Answer correctness

Compares:

- Question
- Expected answer
- Generated answer

Returns a Pydantic `JudgeResult` with:

```text
score: 1-5
reasoning
```

### Faithfulness

Compares:

- Question
- Retrieved documentation context
- Generated answer

The documentation context is treated as the authority for whether claims are supported.

## 15.5 JSON response issue already fixed

Gemini returned judge responses inside Markdown JSON code fences such as:

```text
```json
{ ... }
```
```

Pydantic's `model_validate_json()` failed on the code fence.

The judge code now strips the optional Markdown fence before validating the JSON.

Do not remove this handling unless structured output is later enforced another way.

# 16. Current Evaluation Limitation

The evaluation runner works for at least the first case, but full evaluation is currently blocked by the Gemini API quota.

Observed error:

```text
429 RESOURCE_EXHAUSTED
```

The API response indicated the Gemini 2.5 Flash free-tier request quota had been exhausted, with a limit of 20 requests for the relevant quota.

The evaluation design currently consumes roughly three Gemini generation calls per answerable evaluation case:

```text
RAG answer generation       → 1
Answer correctness judge    → 1
Faithfulness judge          → 1
```

Example first evaluation successfully produced:

```text
Source score:       1.00
Answer correctness: 5/5
Faithfulness:       5/5
```

The full dataset could not be completed because subsequent Gemini calls hit the quota.

## Current decision

**Leave the evaluation design as-is for now.**

Do not redesign it immediately just because of the quota issue.

The model/provider may be changed later. Revisit evaluation cost/architecture when there is a practical need.

# 17. LangGraph — Planned, Not Implemented

LangGraph should be introduced only after the basic RAG foundation is stable.

The point of LangGraph is to provide explicit orchestration and routing, not to turn every function into a node.

The conceptual graph discussed so far is approximately:

```text
User Question
      ↓
Retrieve
      ↓
Evaluate Retrieved Context
      ↓
   Enough evidence?
    /          \
  Yes           No
   ↓             ↓
Generate      Alternative route
   ↓
Verify
   ↓
Response
```

Potential future nodes discussed:

- `analyze_query`
- `retrieve`
- `grade_context`
- `rewrite_query` (optional; only if justified)
- `generate_answer`
- `verify_answer`

State would likely contain values such as:

```text
question
retrieved_documents
rewritten_query
context
answer
sources
retry_count
```

These are planning concepts, not an implemented contract yet.

A retry/loop must have a bounded retry count to avoid infinite retrieval loops.

# 18. Web / Tavily Fallback

The current basic RAG pipeline is documentation-only.

A future requirement discussed is handling cases where the uploaded documentation is not sufficient and an external search may be appropriate.

The current idea is to handle that **when LangGraph is introduced**, rather than adding web search to the basic 2-step RAG now.

Conceptual future flow:

```text
Question
   ↓
Retrieve documentation
   ↓
Enough evidence?
   ├── Yes → Generate → Verify → Answer
   └── No  → Web/Tavily search → Generate → Verify → Answer
```

Tavily is therefore a planned option for a later LangGraph-based fallback/tool node, not part of the current RAG implementation.

No Tavily integration has been implemented yet.

# 25. Security Principles

Current MVP rules:

- Keep API keys in `.env`
- Never commit `.env`
- Do not hardcode secrets
- Do not log secrets
- Do not put secrets into LangSmith metadata
- Validate document types

- Access control
- Rate limiting

# 31. What Should Happen Next

The immediate next step is **not** a retrieval rewrite or multi-hop implementation.

The current preferred sequence is:

## Step A — Evaluation baseline

When the model/quota situation allows:

- Run the complete dataset
- Capture evaluation outputs
- Calculate aggregate results
- Inspect failure cases

Do not prematurely conclude that a retrieval improvement is needed without seeing the evaluation data.

## Step B — LangGraph

Introduce LangGraph around the existing RAG pipeline.

Goal:

- Explicit workflow/state
- Conditional routing
- Bounded retries
- Better orchestration
- A clear reason for using LangGraph

Potential routing:

```text
Question
 ↓
Retrieve
 ↓
Evidence sufficient?
 ├── Yes → Generate → Verify → Response
 └── No  → Fallback/tool route
```

## Step C — Web/Tavily fallback

Potentially introduce Tavily as a tool/fallback inside LangGraph when documentation is insufficient.

Do not add Tavily to the current basic RAG path before the graph exists unless requirements change.

## Step D — Conversation memory

Add conversation/session state once the application needs multi-turn interaction.

## Step E — FastAPI

Wrap the existing application services with a small API layer.

## Step F — Testing / hardening / observability expansion

Expand integration tests, error handling, request-level logging, and trace quality.

## Step G — Docker / deployment

Containerize only after the application boundaries stabilize.

## Step H — Optional frontend

Only add a lightweight UI if it materially improves the portfolio demonstration.
